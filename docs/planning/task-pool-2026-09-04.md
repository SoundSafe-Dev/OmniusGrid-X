## Initiative: proactive incident correlation · L

**Two real systems already exist in this lane and have never been connected.**

`app/services/model_monitoring.py` implements genuine statistics — a KS-test drift detector
(`ModelDriftDetector.detect_drift`, via `scipy.stats.ks_2samp`) and a real Population Stability
Index calculator (`DataDriftMonitor.calculate_psi`). It has had **zero consumers**: the router
is mounted defensively in `main.py` but tagged `unavailable_responses`, and the module's own
comment records that the whole surface 500'd in production for a long stretch because `scipy`
was missing from `requirements.txt` — fixed, but nothing was ever pointed at real data
afterward. Separately, `app/services/correlation_registry_integration.py` already turns AI
findings into real, working `Task`/`TaskBoard` kanban items automatically
(`process_correlation_analysis` → `_create_kanban_task_from_recommendation`) — a genuine
automation pipeline that currently only fires from the LLM-driven spreadsheet-chat engine.

**The initiative is the join, not a new build:** point the drift/PSI detectors at the real
`Telemetry` and `Alarm` tables instead of nothing, and when a detector fires on live data, feed
it straight into the already-working kanban pipeline — an investigation task opens
automatically, with the statistical evidence attached, before a human notices the alarm. Two
fully-built systems that have been running in parallel, wired together for the first time.

This is also where the model-monitoring dashboard earns its keep: a frontend client for
`drift`/`performance` stops being "a missing client nobody built" and becomes the actual
surface where a drift event and the task it opened are visible together. Add a confirmation
step before any MLOps deploy/rollback action this pipeline can trigger — the one piece of the
old ticket list that stays, because it's a safety requirement of shipping this, not a separate
item.

**Done when:** a real drift or PSI event on live telemetry auto-opens a kanban investigation
task carrying the statistical evidence, and both the event and the task are visible in one
place in the UI.

# htreinen — RAG (ingestion, retrieval, vector store, compliance assistant)

## Initiative: compliance evidence export · L

**RAG already does most of what this needs; nothing joins the two halves.**

`api/rag.py`'s `/query` already special-cases compliance questions with a dedicated ERP-context
leg (explicitly commented "never fail a compliance question because the operational leg
broke") — this use case was already designed for, just never finished. Retrieval is a real
hybrid dense+sparse pipeline with cross-encoder reranking (`rag_retriever.py`), backed by an
eval harness at `tests/rag_eval/` that already proves the dense and sparse halves each
independently earn their place (a bare-identifier query only sparse can match; a
zero-overlap paraphrase only dense can bridge). On the other side, `compliance_catalog.py`
already loads structured `Control` records with `implemented_by`/`proved_by` evidence straight
from the YAML catalogue, and `rag.py` already has a presigned-URL `document_link` endpoint for
handing back a source document.

**The initiative is the join:** when RAG answers a compliance question, resolve its citations
against `Control` IDs in the catalogue, and produce one downloadable, audit-ready package —
question, grounded answer, source documents via the existing presigned links, and the matching
control IDs — instead of an answer with citations that point nowhere an auditor can act on.
This turns the assistant from "search the docs" into the thing a customer facing an audit
actually wants: a sellable feature built almost entirely from parts that already work on both
sides.

Two things from the earlier pool are requirements of shipping this, not separate tickets: the
export path needs idempotency protection (`/api/v1/rag` currently has none — a retried export
must not double-generate), and the RAG namespace-topology decision blocks wiring the built
image and secrets it will need in every environment beyond compose. Scope the export itself
with HARSH first (D5) — this is a compliance surface, and building ahead of that sign-off is
how one ships without anyone having agreed what it's allowed to contain.

**Done when:** a compliance question through RAG can be exported as one package with real
control citations, against a scope HARSH has signed off on.

# Alex — intake

## Initiative: smart column-mapping suggester · M

**The matching logic today is a hardcoded dictionary, and the fix reuses infrastructure that
already exists one directory over.**

Every uploaded spreadsheet's headers get canonicalized through `evidence_engine.py`'s
`_COLUMN_ALIASES` — an exact-match dict (`"equipment": "asset_id"`, `"trailer": "trailer_id"`,
and so on) that Alex already owns the code path around, from his `normalize_key` fix in July.
Anything the dict hasn't seen falls straight through to `"unnamed_field"` and silently never
joins — so every new customer's spreadsheet with an unfamiliar header ("Unit #" instead of
`asset_id`) loses a column with no signal to anyone that it happened. There is no fuzzy or
learned matching anywhere in this path today — it's regex and dictionary lookups end to end.

Meanwhile the RAG stack already has a working embeddings client (`inference_client.py`) that
nothing outside RAG has ever called.

**The initiative:** at the exact point `evidence_engine.py` falls through to `"unnamed_field"`,
score the unrecognized header against the known canonical set using that same embeddings
client, and surface a one-click confirm/reject suggestion in `IntakeInbox.tsx` instead of
silently dropping the column. Nothing here requires building an embedding service or a
canonical vocabulary from scratch — both already exist; this is the missing link between them,
and it's a feature a user can watch fix a broken import in front of them.

**Done when:** an unrecognized spreadsheet header gets a suggested mapping in the UI, and a
user explicitly confirms or rejects it rather than the column silently vanishing.

* **Mechanical work doesn't go in the pool.** The test that decides which bucket an item falls
  into: does the fix already have a fully specified answer somewhere (a test's own register, a
  pattern used three times elsewhere in the tree), or does it need someone to decide what
  should happen or design something new? The first is handled directly; the second is a ticket
  — and a ticket should be worth the person's time it's handed to, not a chore with their name
  on it.
* **Every initiative is a join, not a build from zero.** All three were chosen by finding two
  real, already-working things in the same lane that had never been connected — the drift math
  and the kanban automation, the compliance-aware RAG query and the compliance catalogue, the
  embeddings client and the alias dictionary. That's deliberate: real infrastructure already
  exists in every lane, and the exciting version of "what should we build" is usually "what did
  we already build twice, separately, without noticing."
* **HARSH holds both hats deliberately.** A PM decision blocking an engineering initiative (D4
  shaping Kanban's fate, D5 gating htreinen's export) should get answered before the blocked

* **Ratchets only shrink, floors only rise.** `MAX_UNDECLARED`, `MAX_PERMISSIVE`,
